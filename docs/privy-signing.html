How Privy signs (TEE mode, the default)

The browser never holds the wallet key. It holds a short-lived P-256 user key that authorizes API requests. The secp256k1 wallet key is rebuilt from two shares inside Privy's AWS Nitro enclave, used once, and wiped.

Sequence: signMessage("hi") from the React SDK

Step by step

  1. BrowserUser logs in (Google, email, …). Privy issues an access token: a JWT valid for 1 hour, renewed with a 30-day refresh token.
  2. BrowserThe SDK sends the JWT to Privy and asks for a user key.
  3. Privy APIPrivy checks the JWT and returns a time-bound P-256 key it generated, encrypted to a keypair the requester created.
  4. BrowserThe SDK signs the API request itself (not the transaction): canonicalized JSON of method, URL, body and privy-* headers, signed with ECDSA P-256.
  5. BrowserIt calls the Privy API with that signature in the privy-authorization-signature header.
  6. Privy APIThe API attaches the encrypted auth share and forwards everything to the enclave.
  7. TEEThe enclave checks the signature belongs to the wallet's owner and that the policies allow the action, decrypts its enclave share, combines the 2-of-2 Shamir shares into the secp256k1 key, signs, and wipes the key.
  8. TEEThe signature goes back to the API (Privy can also broadcast the transaction).
  9. Privy APIThe browser receives the signature or transaction hash.

Why this matters for Lowki

Privy's Node SDK documents that an app's server can pass authorization_context: { user_jwts: [jwt] } and sign with the user's wallet. So in TEE mode, anything holding the user's access token can move their funds: the app's backend, an XSS that steals the token, or a stolen session. MFA is the only extra protection, and apps opt into it.
