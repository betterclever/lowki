Prove it on your GPU.

A real Privacy Pools withdrawal proof: the audited circuits (1.0.5), a 1,500-leaf pool, made by Lowki's Rust prover on your GPU with WebGPU. Then snarkjs, the standard JavaScript prover, proves the same withdrawal from the same bytes with every core you have. Each proof is checked by both verifiers.

An artistic rendering of the real computation: one point per proving-key base (36,901), streamed into Pippenger buckets, then summed into the proof. The stages replay at 1/12 speed from the measured timings. The timings on the right are real.

Downloads 21 MB of circuit once, then proves twice.

This browser has no WebGPU, so Lowki proves on one CPU thread instead (about 2 s on a fast laptop). The proof is identical; only the speed changes. Try Chrome or Edge on a desktop to see the GPU path.

      Why it kicks

      The same SDK. A different promise.

      Keys on the device

      The seed is made and used in a Rust/wasm worker, wrapped with a key from the passkey's PRF. The server stores a blob it can't open. Neither the operator, Google nor an app can sign for the user.

      A wallet per app

      Every app origin gets its own address, derived on the device, and a pairwise user ID (did:lowki:…). Two apps can't link the same user through Lowki.

      Private sends

      Shield into Privacy Pools and withdraw privately through Kohaku's plugin. The Groth16 proof is made in the browser: 168 ms on WebGPU. Ragequit is an exit nobody can block.

      Anonymous reads

      An Anon-RPC provider mode (Nox, Nym or tor-js, through Kohaku's provider interface), with one isolated session per app address, so the RPC can't join them up.

      ENS stealth names

      alice.lowki.eth resolves to a fresh stealth address on every lookup (ERC-5564, ENSIP-30, verified on chain). A public name without a public payment history. Live on Sepolia.

      Self-hostable

      One server binary, SQLite or Postgres. Any app can run its own server, wallet origin and ENS gateway. Nothing on chain depends on a Lowki contract.

      A Rust core

      Keys, Shamir shares, stealth addresses, Poseidon trees and the prover are Rust, tested against the TypeScript references. JavaScript is bindings only.

      Who learns what.

      Every party Lowki talks to, and what it can and can't see. Where we fall short today, the table says so.

      PartyLearnsDoes not learn
      The app Its own pairwise user ID (did:lowki:…), its own address for the user (and that address's public history), the requests it sends to the wallet, when the user is signed in The user's email or Google account, the seed, the user's addresses or IDs in other apps, private balances
      lowki-server operator Passkey public keys; HMACs of the Google subject and email; the wrapped seed blob and share S (both useless alone); sign-in times; which apps each user gets tokens for, since it mints them; client IPs (in memory, for rate limits). It also serves the wallet code Keys, the seed, PRF outputs, the recovery code, transactions signed on the device, the user's addresses
      RPC provider Today the wallet's reads go through a plain JSON-RPC endpoint: it sees the IP and every address queried, so it can link the per-app addresses one browser looks up With Anon-RPC (Nox, Nym, tor-js): the IP, and with per-address sessions, which addresses belong together. Used for Privacy Pools traffic; not yet wired into the wallet UI
      Privacy Pools relayer The withdrawal it submits: recipient, amount, fee (public once mined); the requester's IP unless it goes through Anon-RPC Which deposit is being spent, or the depositor (hidden by the zero-knowledge proof)
      ASP (0xbow) Every deposit and its depositor address (public on chain) and its approval decision; the IP and timing of approval-set fetches unless through Anon-RPC Which note a withdrawal spends, the recipient's link to the deposit
      ENS gateway operator Every lookup of a .lowki.eth name and every stealth address it hands out, so it can link a name's stealth addresses The viewing or spending key. It can't redirect funds (verified on chain). Senders who derive client-side bypass it
      Google / email provider Google: that the account signed in to the operator's OAuth client (scope openid only). Email: the address and a sign-in code Which app the user was using, addresses, keys
      The chain (public) Each app address and its transactions; shielding into Privacy Pools; withdrawals to a recipient; payments to stealth addresses The link between per-app addresses (unless funded from a common source); the link between a deposit and a private withdrawal; that a stealth address belongs to a name

      Stated plainly: whoever serves the wallet origin could serve code that reads the seed after unlock (self-hosting moves that trust to an operator you choose), and the server operator is trusted for availability and for unlinkability across apps, not for custody.
